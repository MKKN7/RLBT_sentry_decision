## 3. 建议的数据记录粒度（工程建议）

不在此预设固定采样频率。分别保留原生传感器消息、裁判系统事件和策略决策记录，再统一时间基准；采样率与控制频率由实际接口确定。

每条有效观测保留`source`、`source_timestamp`、`receive_timestamp`、`valid`、`confidence`；无法观测的量为未知，不用0代替。跨机器时间先验证同步，再计算数据年龄。规则计时尽量使用裁判比赛时钟与本机单调时钟，记录暂停、重置和时钟异常。

每次宏任务记录开始、结束、持续时长、目标、前置条件、合法动作集合、RL建议、实际执行、BT状态与终止原因；安全抢占、失败和超时不能都编码成普通成功终止。每次命令记录请求与回执，直到确认生效或失败。

比赛结果单独记录基地摧毁、累计控制度、攻击伤害和总剩余血量，保留胜负判定优先级。不能只留下标量reward而丢失原始各项指标。

仿真特权状态与可部署观测分开，避免训练或评估时把未知敌方全状态泄漏给actor。按完整比赛/场景/对手划分训练和评估，避免同一局相邻片段被拆到两侧。

`log_schema.json`是字段说明草案，不是严格JSON Schema验证器，也不是一份样本日志。

## 4. 过洞能力的待采集表

建议每次尝试至少记录：隧道ID、方向、机器人姿态/包络、入口位置误差、速度、三段卡事件时间、身体通过时间、增益确认、碰撞/卡滞/定位失效、是否退回、最终成功原因。通过时间应报告中位数和高分位数，分别统计身体通过率和增益获取率。

3 s触发窗是规则门槛；本机是否能稳定满足，需要实测。在感知误差、板材间隙、场地磨损和网络延迟下留多少余量，应由记录决定。
