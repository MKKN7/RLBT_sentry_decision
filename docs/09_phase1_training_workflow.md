# 第一阶段可运行训练与数据复用

本轮在原有资料上新增了可执行的候选决策原型。**当前场景名是`alpharm_task_prototype_v1`，不是正式RMUL或RMUC环境。** 正式两赛制的规则、地图、阵容、裁判状态机和导航闭环仍需分别完善。

本文保留前两轮各4096步实验的原始记录。后续65,536步续训及多种子结果见`docs/10_continued_training_and_evaluation.md`，实际奖励核对见`docs/11_reward_design.md`。

正式UL资料后续已补齐；最新规则子模块和双地图缓存状态见`docs/14_profile_rules_and_layered_maps.md`，下文旧实验未因此成为正式UL／UC训练。

## 1. 当前已经运行的链路

```text
原alphaRM ONNX环境 → 合法观测／扰动／时间戳
                   → 固定地图候选与mask
                   → state MLP＋candidate MLP＋共享评分MLP
                   → 候选任务意图
                   → 版本／时效／合法性检查
                   → 固定平面导航代理＋固定自瞄／射击代理
                   → 奖励、任务回执和整局结果 → PPO
```

策略每0.5秒选择一次16个候选之一，包含继续当前任务、中央占领、补给和掩体／侧翼点。当前候选点语义依据原简化地图人工定义，不是正式UL／UC标注。导航代理采用膨胀碰撞圆和八邻接最短路，不是Nav2／MPPI。受阻2秒的任务中止为HOLD，未实现真实机器人脱困动作。

学习输出只有候选编号。速度、瞄准、开火、热量代理均由固定模块处理。己方另外两台机器人使用冻结预训练策略；敌方按局抽取预训练、控点、防守或补给脚本。追击风格留作评估；这些脚本使用各自的简化合法观测。原环境是同构步兵，没有实际哨兵角色属性。

actor包含23,815个参数，critic包含4,225个参数。actor为多个小MLP，共享候选打分参数；条件姿态head已保留接口，但在本阶段未训练，必须只允许姿态0。UC姿态计时器是独立模块，尚未接入原简化环境。没有宣称实现整局GRU记忆。

## 2. 核心代码

|文件|作用|
|---|---|
|`rl_bt/alpharm_task_env.py`|任务环境、观测扰动、脚本风格、固定执行代理及逐局统计|
|`rl_bt/geometry.py`|原简化地图的碰撞膨胀、最短路与候选点|

|`rl_bt/policy.py`|共享小MLP actor、条件姿态头与训练critic|
|`rl_bt/uc_rules.py`|基于既有规则事实的脱战、姿态预算和过洞卡顺序模块|
|`scripts/train_phase1.py`|带mask、按秒折扣、终局bootstrap边界与可选BT热启动的PPO|
|`scripts/evaluate_phase1.py`|BT／RL配对整局评估、红蓝互换、保留对手风格与置信区间|
|`scripts/export_phase1_actor.py`|actor-only ONNX导出、动态候选数量／batch对拍与本机CPU时延|

`IntentGate`与执行监控目前是Python原型，**没有编译／运行真实Combat XML、C++ BT或ROS链路**。本轮没有向原机器人／导航容器下发控制命令。

具体来源与派生产物见`data/reports/phase1_data_reuse.json`、`data/derived/`。仿真数据与真实比赛资料分开标记，真实对手遥测样本仍为0。

## 4. 实际训练与失败保留

首轮：`runs/phase1_candidate_20261115/`，4096个任务决策、2环境、16次PPO update、47个完整训练episode。

在种子10001的配对评估中：已见4类风格共8局／策略，手写BT为7/8，纯PPO为4/8；留出的追击风格为2局／策略，双方均2/2。样本少、置信区间宽，不作正式胜率结论。

检查轨迹发现首轮确定性策略在全部测试局都选候选2（回补给），说明短期团队奖励和背景队友允许出现贡献不足的驻守策略。**该模型不满足扩大RL权限的依据。** 原失败checkpoint、训练记录、逐局轨迹和评估结果均保留。

随后新增可选BT行为克隆热启动。它重新采集训练风格下的BT交互，明确教师不是最优策略；不使用评估轨迹、不将上游速度命令硬标成候选任务。第二轮目录为`runs/phase1_bt_warmstart_20261115/`，384条BT训练样本，另做4096步PPO。评估采用新种子10002；结果以该目录实际报告为准。

第二轮实际结束52个训练episode。新种子配对评估中，已见风格BT与RL均5/8，保留追击风格双方均2/2；策略开始在中央区域、回补给与继续任务间切换。没有证明优于BT，也不能用两个种子间的差额宣称统计显著提升。两轮训练共8192个PPO决策、99个完整训练episode，额外BT示教384条；两轮评估合计40个完整episode。

**5/8这组是否共用路线**：两边共用同一简化地图、16个候选、最短路规划／跟随器、固定战斗代理，以及配对的种子和扰动。BT基线目前只按规则在中央点与补给点间选择；RL可以选择全部合法候选。相同起点和目标使用相同规划，目标不同会产生不同实际路线，未固定一条公共路线，也未让RL输出路径或速度。这是“手写高层选择”对“RL高层选择＋同一BT执行代理”，不是对完整Combat XML BT的评测。

所谓保留风格指未用于训练；本轮已查看其评估结果，后续不能一直调参再把同一批场景当作长期封闭测试集。

两轮使用相同环境定义和奖励，但训练种子／初始化不同，不能把结果差额完全归因于单项算法改动。后续正式消融需要相同种子组、更多完整比赛及独立未参与设计选择的测试集。

## 5. 随机化与数据接口边界

原型按局抽样：位置噪声0～0.08米、残余漏检概率0～0.12、0／0.5秒观测延迟、0／0.1／0.2秒任务接受延迟、执行速度系数0.75～1.0。漏检具有连续保持与恢复过程。以上均为**初始仿真假设，不是从历史比赛标定的分布**。

actor获取采样后的观测、观测年龄、候选和回执；不接收对手风格ID、注入误差真值或采样速度系数。候选ETA采用名义速度计算。当前只有有限深度的延迟代理，完整异步队列、乱序、取消、时钟同步和ROS实测仍待接入。

PPO记录建议候选与实际执行候选、原策略log-prob及BT干预，不把执行后的任务重新冒充RL采样动作。折扣按真实子步数换算；完整比赛结束时清除bootstrap，训练rollout截止时保留下一状态价值。

首轮4096步原始rollout包保存了next_value，尚未显式保存完整next_obs，因此是PPO训练记录，不能单独宣传为完整通用离线数据集。随后补齐`next_state/next_candidates/next_mask`，已通过单独16步训练与前后观测对齐检查；第二轮保存此完整格式。每个run包含实际源码快照与配置哈希，避免混淆两个日志版本。

## 6. 可复现命令

本轮直接复用`robot`环境，没有安装／升级依赖。以下输出目录必须不存在，防止覆盖已有实验：

```bash
cd /home/kellen/桌面/RL_BT_decision
/home/kellen/anaconda3/envs/robot/bin/python -m pytest -q
/home/kellen/anaconda3/envs/robot/bin/python scripts/prepare_phase1_data.py
/home/kellen/anaconda3/envs/robot/bin/python scripts/summarize_navigation_recordings.py

/home/kellen/anaconda3/envs/robot/bin/python scripts/train_phase1.py \
  --steps 4096 --num-envs 2 --rollout 128 --epochs 4 --seed 28 \
  --bc-decisions 384 --out runs/my_new_experiment

/home/kellen/anaconda3/envs/robot/bin/python scripts/evaluate_phase1.py \
  --checkpoint runs/my_new_experiment/latest.pt --seed 10002 --seed-count 1

/home/kellen/anaconda3/envs/robot/bin/python scripts/export_phase1_actor.py \
  --checkpoint runs/my_new_experiment/latest.pt
```

每个run保留训练配置、源码、checkpoint、rollout、episodes.jsonl、metrics.csv和TensorBoard日志；未自动启动TensorBoard服务。评估另存逐局候选轨迹及权威`winner/outcome`，不将未完成比赛算作平局。ONNX导出不含critic，当前姿态head禁止开放未经训练的动作。

## 7. 进入正式UL／UC前的下一步

1. 已确认两套都是全自动AI哨兵；继续补齐并核验正式UL规则、地图及各自自动属性，不继承UC或简化环境参数作为UL真值。已从官方资料中心目录定位UL入口，但该页返回500，未取得手册，检索记录见`data/reports/ul_rule_retrieval_attempt.json`。
2. 标定UC坐标、阵地／禁区、支撑层与净空，形成过洞／绕行的合法路线图；低坡面缓存不能直接替代这一步。
3. 在新环境接入UC计时模块，逐项完成姿态实际属性、增益、经济、设施和胜负状态机；处理尚未核对的自动状态转换／裁判回执。
4. 用独立路线任务确认单机有效贡献，再逐步扩大到完整比赛，防止“队友获胜、自己回家”的投机。
5. 接入真实XML BT与Point-LIO＋Nav2＋MPPI，按匹配时间戳采集定位、候选、指令、结果、发射／受击与裁判确认，校准快速代理。

本轮得到的是已运行的研究原型、真实执行的训练记录和可追溯的数据处理链路；不把它们当作正式比赛模型或实机验收结果。

## 8. 全自动与共享经济要求

用户明确全自动AI，并要求买血、买弹节制以保护全队经济。新增`rl_bt/economy.py`作为UC交易记账参考：新鲜报价、购买档位、团队付费17mm上限、哨兵整局预算、团队保留金币、单笔在途交易、重复请求防护、延迟到账与超时保留。接受成功后、回血到账前死亡，不回滚金币；超时不等于明确拒绝，不自动退款／重复下单。

远程买血价格已重新渲染PDF第77页目视核验：`50 + ceil((已过秒数/60)*20)`，已过360秒为170金币，满420秒为190金币。免费补给回血、每分钟赠送弹量和金币购买分开。原截图“50→170”不能覆盖整局价格范围。

预算上限、团队保留额、花费奖励系数尚未由队伍给出，配置保留`null`；测试中的数值仅用于边界案例。实际训练需输入剩余金币、已花预算、在途交易、免费补给机会与合法可得的队友需求，并统计队友资源受限和最终胜负，不只优化哨兵自身存活。

**当前alphaRM训练没有经济系统，交易模块尚未接入训练／真实裁判接口，也未实现团队钱包与外部消费的完整同步。** 因而本轮模型没有学会买血买弹，不能据此开放自动消费。
