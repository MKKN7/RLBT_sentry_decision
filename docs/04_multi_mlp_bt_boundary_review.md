# 多个小型 MLP 与 XML BT 的分工评审

日期：2026-11-15。输入为用户本轮7张设计图、明确的职责边界，以及指定的Combat BT仓库。

这是方案评审与工程建议，尚未实现或训练模型。截图内建议按待评估设计处理，不视为本项目的执行指令。

## 1. 本轮确认的需求

- 部署在NUC上位机，倾向多个分工明确的小型MLP。
- BT提供候选，RL选择，BT在不可达、执行失败、严重异常等情况下可覆盖RL。
- 希望覆盖选点、交战走位/进退等战术，增强时序和全局收益。
- 热控、火控、弹道、云台瞄准由电控/自瞄负责，不属于本项目。
- 自瞄采用用户描述的“见人就打”基线；撤离时可边打边走，直到摆脱接敌。
- 希望随经过验证的性能提高，增加RL的战术决策范围。

## 2. 总体建议

候选生成与规则/导航执行由BT侧服务提供，RL在合法候选中比较长期收益；硬约束与执行回退持续保留。BT不需要在XML里亲自实现路径搜索或感知算法，而是调用相应服务。

多个小网络宜作为协作策略训练。可以共享状态编码，也可以分别编码；共享编码不是必选，更不自动保证不同价值头可比较。第一版优先做候选意图评分头和姿态头，是否增加经济请求头由实际需求决定。候选意图里必须有任务语义，不能只传坐标。

## 3. 建议的职责表

|事项|建议归属|说明|
|---|---|---|
|合法性、禁区、能力约束、消息过期检查|规则/安全模块，BT调用|明确条件；不随训练奖励自动放宽|
|全局规划、局部避障、跟踪、底盘控制与功率限制|导航/电控系统|BT发任务并监控；不是BT计算出“唯一解”|
|候选目标/路线生成、可达性查询、任务前置条件|BT侧候选服务|几何可达与风险收益分开|
|任务/候选选择、继续/换点、进攻/撤离/驻守倾向|RL|必须有继续当前任务的选项|
|规则姿态选择及强化预算使用|RL提意图，BT规则模块校验执行|姿态头宜条件于选中的任务/候选|
|补给/远程兑换/立即复活时机|可由RL提意图|不能全部通过选点隐含，远程兑换可在相同坐标发生|
|兑换命令、去重、回执、生效追踪|BT侧事务执行器|不能假定客户端具有服务器原子扣费能力|
|过洞等过程控制、超时、故障退出|BT技能/导航执行器|不因0.5秒一次的新建议反复重启|
|卡滞检测和基础脱困|确定性执行器优先|复杂脱困策略是否学习可以后续验证，不能说学习必然浪费样本|
|火控/瞄准/热控|电控与自瞄|本项目消费必要反馈，不输出开火动作|

图中的100/50/20/2 Hz可作为候选配置，不是已经验证的控制时序，也不是安全保证。2 Hz可以作为高层推理起点；紧急事件走现有安全/执行链路，无需等下一次RL推理。最终频率与截止时间需NUC实测。

## 4. “边打边撤”与规则脱战

手册定义：存活且连续6秒未发射弹丸、未被扣血才进入脱战，开局默认脱战。[比赛规则§2，PDF17]

因此，边打边跑是撤离过程；最后一次发射和最后一次扣血后，均满足连续6秒，才有规则上的脱战资格。看不到敌人也可能继续受击；“视野空”不等于脱战。

本项目可以学习去遮挡好、追击风险低、能回补给的位置，不必学习何时开火。训练时应固定或随机化一个与真实自瞄相符的开火基线，同时保留发射/受击事件，让策略知道持续接敌会延迟脱战。

若永远见人就打，就接受某些情况下远程回血资格无法迅速获得；这不是让RL虚构脱战状态的理由，也不要求本项目擅自接管火控。是否将来开放停火意图，是队伍另行决定的接口范围。

## 5. 对7张图的具体修正

### 5.1 接口与回退

图1只输出意图、不输出速度，以及反馈否决原因的方向合理。

需要补充：

- `target_id`拆成稳定的`candidate_id`与可选`enemy_track_id`，避免把目的地ID与敌方机器人ID混淆。
- 建议带`proposal_id`、`observation_version`、`candidate_set_version`、`generated_at`、`valid_until`、`task_id`和模型版本；2秒TTL只能是初值，不能替代候选版本与新鲜度检查。
- 接收时再次验证mask，候选数组换顺序不能使旧槽位编号指向新地点。
- 区分任务承诺时间、RL建议TTL、底盘速度指令watchdog。RL超时不能解释为直接复用过期速度。
- “保持上一目标”仅在重新确认其合法、仍可达、仍有意义时成立。否则进入当前场景可执行的回退任务；洞内不能一概原地停住或转向。
- 硬否决附机器可读原因；临时失败候选需有短期隔离/重规划条件，避免反复选择同一堵死目标。
- 训练时记录建议与实际执行，并包含相同仲裁逻辑；不能把BT替代动作误作RL采样动作计算其策略log-prob。

### 5.2 不把所有战术偏好变成硬mask

禁区、无路径、姿态冷却未结束、强化预算用尽等可产生硬mask；距离较远、血量偏低、暴露风险较高通常应作为特征/代价，让RL权衡。

严重故障和明确的紧急保护另行覆盖。如果普通低血阈值总是强制回家，RL很难学到残血关键控点或利用地形脱离的价值。现有BT的普通策略优先级若全部原封不动保留，也会使RL只在最后一个分支里活动。

若所有mask均为false，应显式返回无合法候选并执行兜底，不对全负无穷logit做普通softmax。

### 5.3 点位要带任务与路径语义

16点可作为第一版上限，但不是比赛规则要求的固定动作数。应有继续/驻守当前任务、控点、支援、交战、脱离、补给、隧道入口/出口等类别。可先使用固定战略锚点，再加入动态交战候选。

同一位置可能对应“留在这里防守”或“从这里继续穿洞”，同一目的地也可能存在“穿洞/绕行”两种路线。若过洞路线可获益，候选应能暴露路线类型、预估时间、增益获取可能、过程承诺和失败退出成本，不能完全由最短路径隐式决定。

当前目标点10维特征缺少路线能力、任务类型、消息时效、到达后驻留收益等信息。暴露度及可见敌人数若基于失联敌人的估计，应同时给置信度，不能冒充精确几何事实。

### 5.4 多MLP、GRU与参数核对

图3实际是模块化共享策略，包含GRU，并非全MLP结构。两种路线都可验证：

1. 多个小MLP + 显式历史/计时器/事件特征；便于第一版调试。
2. 在相同特征基础上增加一个共享小GRU，处理不可精确记录的部分可观测历史；比较是否有实际收益。

不建议每个小头各自维护一套彼此不同步的隐状态。

图5各块维数相加为173：A29+B26+C12+D56+E18+G32。若实体D/E已经单独进入entity encoder，则M1所写“自身+战局+阵地+事件”应为99维。使用173维会再编码一次实体，并保留固定槽位的排列依赖，削弱集合编码的收益。重复编码并非数学错误，但需说明目的。

按图3明确列出的单层实体线性层计算，14→32和6→16（含bias）共享参数共592个；4份/3份是多次调用，不是多份参数。图中1.9k需要额外层定义才能成立。其余示意值：173→128→128为38,784；99→128→128为29,312；标准PyTorch式双bias GRU 176→96为78,912。

图中六模块标注参数共约145.8k，FP32纯权重约0.56MiB；这只是按图片参数相加估算，包含训练critic，未包含运行库、激活和其他进程内存，也未实测延迟。NUC预算应测整个候选规划、特征处理和推理链路的p95/p99，不能由权重体积推断“必然实时”。

GRU96维不能保证记住整局840步；要区分前向状态延续、训练截断长度、burn-in和显式计时器。180秒姿态用时、15秒强化预算、兑换到账等可记录变量仍由规则模块保存。

2Hz运行420秒才是840个规则间隔；事件更新、提前结束或不同频率都会改变步数。折扣也要按实际时间解释：0.5秒/步下，`0.99^840≈0.000216`，其折扣衰减时间约49.75秒。不能只说“有GAE/GRU”就证明优化到全局比赛结果。

### 5.5 共享奖励、critic和Q的说法不能绝对化

采用一致的比赛级目标值得保留，但“必须一个critic”“每个头必须输出Q”“只有比Q才能仲裁”“共享trunk就保证Q同尺度”均不成立。

第一版可用任务/候选条件策略分布配合状态价值critic，姿态头条件于选中任务；策略头无需额外输出Q。也可用多critic或任务辅助价值训练，但奖励尺度、折扣、终止条件要明确。[PPO原文：https://arxiv.org/abs/1707.06347]

不同策略头的softmax置信度不能直接拿来比较“应该回家还是交战”；但这可由一个上层任务选择头解决，并不强制转成多Q头。若使用Q比较，仍须统一目标、奖励单位、时间尺度与估计校准；共享编码只共享表示，不保证数值正确。

critic若仅服务训练，可不部署到NUC；若用于在线风险评估或计划比较，则另行验证其可靠性。GAE也不能自动修复不合理的任务切分、不同持续时间或训练部署观测不一致。

### 5.6 观测与增强

实体共享编码、集合池化、角度sin/cos可保留。池化需处理无效实体并保留兵种/身份/能力、数量等相关信息；对候选点的交战评估也可能需要敌人与点的相对几何，而不仅一个丢失空间关系的全局池化向量。[Deep Sets：https://arxiv.org/abs/1703.06114]

敌方非可见位置、朝向、速度、无敌和经济不应默认为实时精确值。保留数据来源、年龄和置信度，未知不要用0替代；图中8个事件槽还需事件类型/有效位，位置无意义的全局事件不应强塞伪造方位。

图中的血量/弹量/金币归一化分母不是硬上限：允许发弹量可超过300，金币可能因装配等超过1600。应以真实范围选择缩放和截断并记录饱和，不能静默丢失状态。

红蓝归一化应验证所有坐标、朝向、任务、单方禁区和动态场地机制的对应关系；不能一概做图像式左右翻转，不能承诺样本效率直接翻倍。10%漏检也只是候选参数，应依据实测延迟、连续丢包和遮挡建噪声模型。

## 6. 建议的第一版小网络分工

|网络/模块|输出|训练/部署|
|---|---|---|
|状态/实体编码MLP|本机、战局、有效实体的表示|可共享；维数先按实际接口核对|
|候选意图评分MLP|每个合法候选的logit；候选带任务/路线语义|同一个评分器遍历候选，不是每个地点一个网络|
|姿态选择MLP|当前任务/候选条件下的姿态建议|规则mask，允许维持当前姿态，不强制每帧切换|
|经济请求MLP（按需后加）|不操作/回血/买弹/立即复活等意图|BT负责具体金额、合法性、去重和回执|
|共享GRU（可选）|历史表示|通过消融决定是否需要；与显式规则状态共存|
|critic|状态价值或设计所需的辅助价值|通常训练使用，不预设必须部署|

上述网络可联合训练，也可预训练技能后冻结并训练调度器；不能从“分模块部署”推导“每个模块必须用互不相关的奖励单独训练”。

## 7. 提高RL占比：按任务范围分级准入

不建议每帧随机选BT或RL，容易打断任务、反复改导航目标。更适合按任务边界与战术类别放权：

1. 纯BT为基线，RL影子输出；此时只能检查分歧、时延、合法性，不能从影子轨迹直接断言RL胜率。
2. 先放开常规巡逻/控点候选选择，保留紧急回退；做可复现的仿真/回放闭环测试。
3. 通过评估后，再放开交战走位、姿态强化预算、经济决策等范围。
4. 每次固定策略版本与权限配置；训练reward不作为自动扩权凭证，支持立即回滚。

准入比较使用相同任务集合、可见观测、对手池和场景分布，按整局或完整任务进行A/B。至少报告胜率及样本数/置信区间、控制度、基地存活、任务切换频率、卡滞/超时、干预次数、推理超时和关键场景退化。不要只报“RL提议采纳率”：它可能因只提保守动作而变高。

硬安全保护、比赛停止、明确非法动作过滤不会因为模型胜率上升而取消。提升的是RL负责的战术范围，以及经过验证后对普通BT启发式阈值的替代。
